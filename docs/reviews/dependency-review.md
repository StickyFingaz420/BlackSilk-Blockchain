# Dependency and cryptographic-library review

Status: **internal review (2026-09-24; RustSec check and corrections 2026-09-25;
graph review and enforcement W3-44 2026-09-28, section 7), not an independent
audit.**

**Scope.** Every third-party crate that security-critical or consensus-critical code
depends on: what it is used for, how it is pinned, what `unsafe` or native code it
brings, and the risk of upgrading it.

**Advisories:** `cargo deny check advisories` (RustSec database of 2026-09-28) finds
no vulnerability, unsound, unmaintained (other than the reviewed `paste`) or yanked
crate in either lockfile (section 7); the CI job `audit` runs `cargo audit` as a
second opinion (section 5).

## 1. Pure Rust

"Pure Rust" here means **no foreign code** (no C, C++ or assembly compiled or linked
into a shipped binary), not "no `unsafe` in dependencies". Since W3-44 (2026-09-28)
it is checked on every push and weekly by the CI job `deny`, not by hand:

| Layer | Check | Where |
|---|---|---|
| Named crates | `cc`, `cmake`, `bindgen`, `cxx`, `cxx-build`, `autotools`, `nasm-rs`, `pkg-config`, `vcpkg` and the C-library bindings (`openssl-sys`, `ring`, `aws-lc-sys`, `zstd-sys`, ...) are banned in the whole graph, dev-only crates included | `deny.toml` `[bans] deny` |
| `*-sys` names | every `*-sys` crate in either lockfile is on a reviewed list | `.github/scripts/sys-crates.sh` part 1 |
| Build scripts | only an exact list of crate versions may have a build script; a new build-script crate, or a new version of one, fails until its `build.rs` is read and listed | `deny.toml` `[bans.build] allow-build-scripts` |
| Build-time files | every crate with a build script or a proc macro, and every dependency of one, is scanned: a native executable, an archive (pre-built object or library) or a script fails unless allowed by exact crate version and path | `deny.toml` `[bans.build]` (`executables`, `include-archives`, `bypass`) |
| C per release target | for each release target, the resolved graph (normal and build edges) holds no C build helper, no build script that starts a C compiler, assembler or C build tool or reads `CC`/`CXX`, and no C/C++/assembly source or native object anywhere; the repository's own tracked files likewise | `.github/scripts/sys-crates.sh` part 2 |
| `unsafe` inventory | every crates.io crate of the release graph with its count of `unsafe` lines (a report, not a gate) | `docs/reviews/unsafe-inventory.md`, generated by `.github/scripts/unsafe-report.sh` |

**Result (2026-09-28, W3-44):** all layers pass. The release graph
has no C, C++ or assembly source and no build script that compiles native code. The
only native artefacts are the pre-built Windows import libraries of
`windows_x86_64_msvc` (OS API stubs, no code), allowed by exact version and path.
The build scripts in the graph were read: they probe the `rustc` version, emit
`cfg`s, or add the import-library directory to the link search path.

**Negative runs (the checks do fail):** in a working tree, reverted afterwards, adding `cc` as a
build-dependency of `rpc` with a `build.rs` that starts `gcc` made `cargo deny check
bans` fail (`cc` banned) and `sys-crates.sh` fail four times over (the helper in each
release target's graph, the `.c` file inside `cc`, and the build script's compiler
call). Adding `ml-kem` with `hazmat` to `p2p` (inline, as a dependency table, renamed,
or forwarded from `[features]`) and a call of `encapsulate_deterministic` in `p2p`
made `hazmat-policy.sh` fail. None of this was committed.

**Test oracles are not product code** and stay outside the product workspaces with
their own locks: libFuzzer (C++, `fuzz/`, allowed there only as the harness's
dependency, `fuzz/deny.toml`), the C++ RandomX reference generator and the Python
vector scripts (test tooling, decisions "Agent 01" and "Agent 05").

**`unsafe` code:**
- **Workspace crates** declare `#![forbid(unsafe_code)]` at every crate root of the
  root workspace (CI job `lint`). Outside it: the zkVM guest SDK (`zkvm/sdk`) has one
  `unsafe` block, its `ecall`, which runs inside the VM; the guest programs
  (`zkvm/guests/`, their own workspace) use no `unsafe` but do not declare the
  attribute.
- **Dependencies** contain `unsafe` internally (OS bindings, the async runtime, SIMD
  field arithmetic and ciphers, zeroization, lock-free structures): see
  `unsafe-inventory.md` for the per-crate counts.

## 3. Plonky3 in detail

### 3.1 What is relied on

- **Soundness** of the batch STARK with LogUp lookups, FRI with hiding, and the
  Poseidon2 duplex challenger. Parameters: BS-ZK-3 (`zk/src/params.rs`, zk.md §9.3; BS-ZK-4 pending); the security bits are
  computed by the project's own tested calculator, not taken from the library.
- **Zero knowledge** of the hiding mode (`HidingFriPcs`, `MerkleTreeHidingMmcs`),
  claimed only as statistical and conditional (zk-coverage.md). Everything private in
  PX rests on it (privacy-review.md §2.2).
- **Poseidon2 over BabyBear, width 16, Plonky3's default constants**, generated by the
  Poseidon2 authors' script. It is used for:
  - Merkle trees and Fiat–Shamir inside proofs;
  - every PX hash (commitments, nullifiers, tree, program ids), through `HostPerm`;
  - the zkVM's `POSEIDON2` table and interpreter.

  One implementation serves all three, so they cannot disagree.

### 3.2 The local patches

- **Files:**
  - `p3-fri/src/hiding_pcs.rs`: `get_quotient_ldes` (ZK-F11, completed by ZK-F28)
    and `commit` (ZK-F21), with a shared `widen` helper and its equivalence test;
  - `p3-merkle-tree/src/hiding_mmcs.rs`: `commit` (ZK-F11);
  - `p3-dft/src/radix_2_dit_parallel.rs`: the three twiddle caches (ZK-F21);
  - `p3-batch-stark/src/prover.rs`: `prove_batch` (PXDET-1, 2026-10-04; the only
    change that is not about locks, see below).
- **Lock-scope change** (the first three files): no `spin` lock is held across rayon work any more. That was first
  claimed after ZK-F21 and was not yet true: one site remained, fixed in ZK-F28.
  Every `lock()` in the patched crates was then re-checked.
  - Random values are drawn under the lock, which is then released.
  - Twiddle tables are computed before the write lock is taken.
- **Review of the other locks in the Plonky3 code we run:**
  - `Radix2DFTSmallBatch` (FRI prover) already computes outside its lock;
  - `Radix2Dit`, the monty-31 DFT and the goldilocks MDS are not used.
- **PXDET-1 change** (`p3-batch-stark`): the quotient values are still computed in
  parallel, then the `get_quotient_ldes` calls run sequentially in instance order,
  so each instance draws the same hiding randomness upstream draws on one thread.
  The verifier and the proof format are unchanged (third_party/README.md).
- **Verified (re-checked 2026-09-27 for the first three; `p3-batch-stark` added
  2026-10-04):** `diff -r --strip-trailing-cr` against the
  registry copies shows exactly these four files (plus upstream's `Cargo.lock`,
  `.cargo_vcs_info.json` and `Cargo.toml.orig`, which were removed). The rest of
  `third_party/` is verbatim upstream 0.7.0. `hiding_pcs.rs` also carries two
  test-only additions (the `widen` equivalence test and the mask-`R` shape test).
- **Correction (2026-09-25):** an earlier version of this section said the PX proofs do
  not use upstream's Merkle path pruning. They do: FRI in 0.7.0 opens every query batch
  through `open_multi_batch`, whose multiproof is pruned. That is the only source of
  proof-length variation (privacy review P-5).
- **Evidence and removal criteria:** `third_party/README.md` and AUDIT.md ZK-F11 and
  ZK-F21.

### 3.3 Upgrade risks (why everything is pinned exactly)

| Change upstream | Consequence here | Guard |
|---|---|---|
| Poseidon2 constants or round structure | Every PX commitment, nullifier, root and program id changes: a hard fork, and existing records become unspendable | `zk/tests/pins.rs` pins the permutation to a known-answer vector; `px/tests/proof.rs` pins the kernel program id |
| Proof encoding or transcript order | Old proofs stop verifying (mempool); the chain's historical proofs would need the old verifier | `PROOF_VERSION` byte; strict canonical decoding |
| Soundness fixes | Must be taken, which may need a coordinated upgrade | Exact pins make every upgrade an explicit, reviewed change |
| The ZK-F11 and ZK-F21 hangs fixed upstream | The local patches can go (re-check every `spin` lock first) | `third_party/README.md` |

**Upgrade procedure:**
1. Move the exact pins together.
2. Re-run the full suite: the mutation tests, the forgery-analysis tests, the
   parameter tests, `pins.rs` and the stress harness.
3. Re-derive the kernel program id.
4. Update this file.

## 4. Determinism

- **Consensus results are deterministic:** verification, hashing, state transitions
  and fee rules use no floating point, clocks or randomness.
- **Hash maps** are either used for lookups only or sorted before iteration where the
  order matters.
- **Proof bytes** are reproducible from (witness, seed) since the `p3-batch-stark`
  patch (PXDET-1, third_party/README.md). Upstream draws the quotient randomness in
  scheduling order. Consensus does not depend on reproducible proofs.
- **Builds:** the kernel guest rebuild was byte-identical; its program id is pinned.
