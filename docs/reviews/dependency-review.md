# Dependency and cryptographic-library review

Status: **internal review (2026-09-24; RustSec check and corrections 2026-09-25), not an
independent audit.**

**Scope.** Every third-party crate that security-critical or consensus-critical code
depends on: what it is used for, how it is pinned, what `unsafe` or native code it
brings, and the risk of upgrading it.

**RustSec:** `cargo audit` against the current advisory database found no
vulnerabilities (§5).

## 1. Pure Rust

No crate in the normal or build dependency graph uses:
- a C or C++ compiler (`cc`, `cmake`);
- `bindgen`;
- `pkg-config`.

The only `links` keys are:
- `rayon-core`, a marker with no native library;
- `wasm-bindgen`, for wasm targets only.

Details: `docs/reviews/zk-security-review.md` §6. `unsafe` code:
- **Workspace crates** declare `#![forbid(unsafe_code)]`, except the zkVM guest SDK's
  `ecall`, which runs inside the VM. Since this review this also covers
  `tools/labnet`.
- **Dependencies** contain `unsafe` internally (SIMD field arithmetic, zeroization,
  lock-free structures). "Pure Rust" here means no foreign code, not no `unsafe`.

## 3. Plonky3 in detail

### 3.1 What is relied on

- **Soundness** of the batch STARK with LogUp lookups, FRI with hiding, and the
  Poseidon2 duplex challenger. Parameters: BS-ZK-2 (zk.md §4); the security bits are
  computed by the project's own tested calculator, not taken from the library.
- **Zero knowledge** of the hiding mode (`HidingFriPcs`, `MerkleTreeHidingMmcs`).
  Everything private in PX rests on it (privacy-review.md §2.2).
- **Poseidon2 over BabyBear, width 16, Plonky3's default constants**, generated by the
  Poseidon2 authors' script. It is used for:
  - Merkle trees and Fiat–Shamir inside proofs;
  - every PX hash (commitments, nullifiers, tree, program ids), through `HostPerm`;
  - the zkVM's `POSEIDON2` table and interpreter.

  One implementation serves all three, so they cannot disagree.

### 3.2 The local patch

- **Files:**
  - `p3-fri/src/hiding_pcs.rs`: `get_quotient_ldes` (ZK-F11) and `commit` (ZK-F21);
  - `p3-merkle-tree/src/hiding_mmcs.rs`: `commit` (ZK-F11);
  - `p3-dft/src/radix_2_dit_parallel.rs`: the three twiddle caches (ZK-F21).
- **Change:** no `spin` lock is held across rayon work any more.
  - Random values are drawn under the lock, which is then released.
  - Twiddle tables are computed before the write lock is taken.
- **Audit of the other locks in the Plonky3 code we run:**
  - `Radix2DFTSmallBatch` (FRI prover) already computes outside its lock;
  - `Radix2Dit`, the monty-31 DFT and the goldilocks MDS are not used.
- **Verified:** `diff -r` against the registry copies shows exactly these three files.
  The rest of `third_party/` is verbatim upstream 0.7.0.
- **Correction (2026-09-25):** an earlier version of this section said the PX proofs do
  not use upstream's Merkle path pruning. They do: FRI in 0.7.0 opens every query batch
  through `open_multi_batch`, whose multiproof is pruned. That is the only source of
  proof-length variation (privacy review P-5).
- **Evidence and removal criteria:** `third_party/README.md` and AUDIT.md ZK-F11 and
  ZK-F21.

### 3.3 Upgrade risks (why everything is pinned exactly)

| Change upstream | Consequence here | Guard |
|---|---|---|
| Poseidon2 constants or round structure | Every PX commitment, nullifier, root and program id changes: a hard fork, and existing records become unspendable | `zk/tests/pins.rs` pins the permutation to a known-answer vector; `px/tests/proof.rs` pins the kernel program id |
| Proof encoding or transcript order | Old proofs stop verifying (mempool); the chain's historical proofs would need the old verifier | `PROOF_VERSION` byte; strict canonical decoding |
| Soundness fixes | Must be taken, which may need a coordinated upgrade | Exact pins make every upgrade an explicit, reviewed change |
| The ZK-F11 and ZK-F21 hangs fixed upstream | The local patches can go (re-check every `spin` lock first) | `third_party/README.md` |

**Upgrade procedure:**
1. Move the exact pins together.
2. Re-run the full suite: the mutation tests, the forgery-analysis tests, the
   parameter tests, `pins.rs` and the stress harness.
3. Re-derive the kernel program id.
4. Update this file.

## 4. Determinism

- **Consensus results are deterministic:** verification, hashing, state transitions
  and fee rules use no floating point, clocks or randomness.
- **Hash maps** are either used for lookups only or sorted before iteration where the
  order matters.
- **Proof bytes** are *not* reproducible from a seed, upstream or patched: the lock
  order is scheduling-dependent (third_party/README.md). Nothing depends on
  reproducible proofs.
- **Builds:** the kernel guest rebuild was byte-identical; its program id is pinned.
